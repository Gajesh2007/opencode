Start an independent child agent for a concrete unit of work that can proceed in parallel with your own work. Child agents share the workspace, so divide work by files or responsibilities to avoid edit conflicts. The child returns its final answer to your direct-parent mailbox and resumes the parent when needed; this tool returns immediately with its canonical task path and session id. Use task_status with that session id to read the child's output at any time.

Spawned agents can recursively use spawn_agent for their own well-scoped work. All descendants share the root collaboration control plane. There is no fixed limit on active subagents; only an explicitly configured concurrency limit applies. This tool does not grant permissions: inherited and agent permission rules still apply, and explicit denies win.

`fork_turns` defaults to `"none"`, creating a fresh child session from the task message alone. Prefer giving the child sufficient context in `message` instead of using `fork_turns: "all"`: `"all"` copies the complete conversation into the child and, in multi-agent systems, can encourage recursive subchat loops. Use `"all"` only when the child genuinely needs the complete current conversation, or a positive integer to retain only that many of the latest user turns and their completed context. These fork modes are available to nested children too. Keep task names unique among direct children.

Optional `model` (`provider/model`) and `variant` select the model and model-specific reasoning effort for this child only, without changing other children or agent defaults. Omitted selections use the selected agent's defaults, falling back to the parent's model and settings. Changing model without variant uses that model's configured agent variant or `"default"`, not the old model's effort. Use `variant: "default"` to clear named effort. `reset_model: true` selects current agent/parent defaults and cannot be combined with `model` or `variant`. Selections must respect configured provider/model restrictions and inherited service-tier/upstream pins; incompatible selections are rejected. Success reports the effective model and variant. Later, the direct parent can change them through `followup_task` only while this child is idle; omitted followup selections preserve the child's latest effective selection.
